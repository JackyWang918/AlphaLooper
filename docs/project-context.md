# 项目目的与接续说明

最后整理：2026-09-21。本文用于跨电脑、跨 Codex 会话继续项目，无需用户重复背景。实际代码能力以当前仓库与验证结果为准。

## 1. 用户为什么做这个项目

用户每天参与 Binance Alpha 交易积累积分。目前需要花时间手动反复买卖，为了尽快完成任务有时交易损耗较大，曾出现一天损耗超过 10 U 的情况。用户描述为“被夹”，但尚未通过交易记录区分链上夹子、价差、滑点或价格波动等具体原因，不应直接下定论。

用户希望构建一个浏览器自动交易辅助程序：通过行情数据和规则计算价格，自动输入价格、数量并执行买卖；订单一定时间未成交时，能按规则撤单调整，避免一直买不到或卖不出。长期希望晚上运行，减少重复劳动与赶时间交易带来的损耗。

用户不是始终交易同一个币。某些币的 4 倍活动有时限，当前人工寻找适合当天交易的币，因此必须允许手动修改交易币种或链接，不将 DGAI 固定为唯一交易对象。

## 2. 用户已明确的工作方式

- 用户自己登录，出现风控验证时自己处理。
- 初期可以约半个月守着电脑验证，不要求一开始就无人值守。
- 初期最关心的是浏览器能否受控：把其他程序算出的价格和数量填入页面，执行买卖操作。不要把账户信息获取再次当成唯一的首要问题。
- 行情计算、浏览器执行可以是独立模块，通过指令连接。
- 用户希望有数据展示和交互界面。
- 前后端放在同一个项目文件夹、同一个 Git 仓库中。
- Python 用 uv；前端用 npm；本地 SQLite3；源码运行，暂不考虑部署或打包。
- 2026-09-21 用户在公司，不方便频繁操作界面，登录后的测试留到回家继续。此为当时安排，不是永久禁止测试。

## 3. 策略方向与最新决定

用户已澄清：根据过去的数据估算合理买卖价格，挂单等待；超时未成交就撤销、重新估价并重挂。不是以快速买卖作为默认策略。详细规则与尚待确认的细节见 [首轮策略约定](strategy.md)。

助手建议的优先顺序为：避免误操作和失控持仓 → 控制损耗 → 完成目标有效交易量 → 缩短时间。这个顺序尚未得到用户明确确认，不得作为已经敲定的策略。

最新已确定：每轮 50 U；等待时间初值 5 分钟；买入允许追随新行情重估；卖出能回本时参考卖一，未回本时重算卖价；亏损阈值 2%，每分钟结束后检查；触发后允许根据最新买盘持续调整至卖完；整场测试累计损耗预算不超过 10 U。用户举例以买盘第 6 档作为主动卖出价格。

2026-09-21 用户核对平台后提供买入、卖出手续费各 0.01%（每侧 1 基点）。研究界面默认值已更新，确认文字随输入动态换算百分比；后端继续按传入的 `fee_bps` 使用 Decimal 计算。这是用户提供的费率，非系统自动查询结果。

用户最新要求推进自动实盘交易，并记录委托及成交、自动计算累计盈亏。每日目标已更正为 **32,768 分**（替代此前的 32,678）；按用户提供的每买入 1 U 计 4 分规则，对应累计买入成交额 **8,192 U**。仅实际买入成交金额计分，卖出不计分；平台实际积分口径尚未核验。这些是新增需求，真实执行尚未实现；模拟任务持久化及预计积分统计已实现，不能当作账户真实积分。

用户进一步确认：每日积分达标后停止新买入，剩余持仓转主动退出、优先尽快清仓，卖完结束当天任务。持仓从本轮首笔买入成交开始计时，满 **30 分钟**仍未卖完即转主动退出，不要求先亏损 2%；部分成交及撤单重挂不重置持仓计时。30 分钟不是保证清仓期限。这两条规则已接入模拟器并通过测试，尚未接入真实执行。

其他尚未确定的参数和口径：

- 每日统计重置时间、整场测试损耗与每日损耗的关系。
- 更精确的费用来源、真实执行损耗和预算预留参数。用户已确认损耗含费用与预计退出浮亏，预算触发后停止新买入并处理已有持仓。
- 夜间运行窗口、任务截止时间。
- 历史窗口、波动算法和报价偏移参数待实验；用户已确认每张普通单 5 分钟，部分买入到期后先卖已有数量、不补足。
- 主动退出重挂间隔、买盘不足六档或深度不足的实盘处理；模拟阶段的试验规则见策略文档。
- 活动倍率和有效期如何核实、过期如何处理。

不要把未定细节当作已确认，也不要承诺一定成交或绝对损耗上限。

## 4. 已实现的程序能力

- FastAPI 后端与 Vue 3 + TypeScript + Vite 控制台。
- 通过 Playwright 独立进程启动本机 Chrome，使用 `data/browser-profile/` 保存本地登录数据。
- 控制台输入 Alpha 链接，打开受控标签页，查询标题和地址。
- 读取中文 Alpha 表单中的代币、USDT/USDC 计价币、买卖方向与输入步长。
- 仅填表：核对目标链和合约、币种和计价币，切换方向，填写价格与代币数量，再回读核对。
- 遮挡弹窗、币种不符、精度不符、方向变化等异常会停止操作；不强行穿过遮挡层。
- 页面操作串行执行，忙时拒绝其他操作；刷新控制台不会重放指令。
- SQLite 已持久化模拟任务、委托、成交与事件记录（迁移 0002）。服务端持有任务状态，事件编号去重、版本冲突检查和事务保证一次记账；真实订单汇总账本另外使用迁移 0004，见第 10 节。

新增：公开行情接入，已收盘 1 分钟 K 线、成交量、盘口展示，参数化挂价试算，以及显式成交事件驱动的订单流程沙盒（超时、部分成交、分钟损耗检查、主动退出及预算限制）。仅模拟，并未连接浏览器下单。浏览器操作反馈仍在页面内存；沙盒任务、参数、委托、成交及事件保存在 SQLite，刷新或重启后可载入。模拟成交由用户显式输入，手续费按假设费率以计价币记账。已实现累计买入额、预计积分、已实现盈亏、剩余成本和按买盘估算的含退出费浮盈亏。盘口过期或深度不足时浮盈亏未知，不使用旧行情冒充实时估值。

当前没有：真实订单提交、真实订单/成交监听、真实撤单重挂、自动实盘循环、自动选币、平台实际积分核验、真实交易持久化指令队列或 WebSocket 状态推送。

不要将可见的买卖切换 tab 当作最终买卖提交按钮。当前代码不定位或点击最终提交按钮；未登录时该区域显示登录入口。

## 10. 真实订单汇总账本（最新决定，替代此前逐笔核验方案）

用户明确校正：直接使用平台订单汇总，订单 ID 去重更新；每侧手续费按实际成交额 × 0.01% 估算。不再要求逐笔成交 ID、详情读全、明细量对账或真实手续费币种核验作为入账前提。

已移除逐笔详情解析和预览。只读读取器在展开区域仅取订单 ID，关联其紧邻的汇总行。新增迁移 0004 订单表，账本名称 + 订单 ID 唯一；重复读取覆盖最新汇总，拒绝过期、回退或身份冲突。部分成交/撤单按平台实际成交额统计，买入额 × 4 为预计积分，卖出不计分。金额 Decimal 计算。

控制台改为“真实订单账本与统计”，展示订单、累计买卖额、估算手续费、预计积分、预计已实现盈亏。缺失买入成本或订单顺序不明时盈亏未知，剩余数量仅表示已记录订单差额。每日重置仍未定义，不能称为今日账户全量数据；按币种/计价币分组。

当前需要手动在平台历史委托展开订单以暴露 ID，读取器不会自动展开、翻页或交易。账户账本名称由用户选择，换平台账户应换名称；没有自动账户识别。原始快照保留排查，与正式汇总订单和模拟账本分离。

此前已登录真实页面只读验证了历史委托汇总行和展开订单 ID 的结构，真实数据只保存在本机数据库，不进 Git。仍没有真实订单提交、撤单或自动实盘循环。

本轮验证：57 项全量测试通过，随后新增的 ID-only 长详情测试及订单 API 去重/载入测试分别通过（共 59 项）。Ruff、前端构建和 Alembic 一致性检查通过。本机已升级数据库并重启后端、重新打开 Chrome 交易页。用此前保存的真实卖单快照导入 1 笔订单，重复导入数量及统计不变，控制台已显示估算手续费和成本待补齐；这不是重启后重新读取全量真实订单的验收。没有下单或撤单。
