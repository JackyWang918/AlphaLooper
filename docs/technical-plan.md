# AlphaLooper 技术方案

状态：独立进程浏览器启动、打开页面、状态查询及中文 Alpha USDT/USDC 表单的仅填表与回读核对已实现；订单提交尚未实现。真实未登录 DGAI 页面买入填值通过，卖出切换因平台弹窗阻挡待用户处理后继续验证；登录后页面验证待完成。

页面定位依据实际观察到的 `#limitPrice`、`#limitAmount` 与中文买卖 tab 的 `aria-selected` 属性，不定位提交按钮。填表前后核对 URL 中的链和合约、表单币种与计价币、方向及价格/数量步长。填写前执行控件可点击性检查，防止直接填值穿过遮挡弹窗。精度不符或回读值不一致时停止，不自动修正金额或重试。

当前实现使用 HTTP 同步返回浏览器操作结果，忙时拒绝新操作，不自动重试。刷新控制台重新查询浏览器状态，真实交易暂未引入持久化指令、WebSocket 或成交监听；这些在真实表单适配后逐步实现。

新增独立研究模块：公开 Alpha 行情通过 httpx（可配置 curl 兼容传输）获取，代币元数据缓存 5 分钟；K 线/盘口/ticker 并行读取。策略使用 Decimal，API 以字符串传输小数。研究 API 与浏览器执行器隔离；持久化模拟任务状态由后端持有，SQLite 保存任务、委托、成交及事件，前端只传版本号、事件和行情快照；旧无状态 `/simulate` 接口保留用于独立试算。数据库事务、事件唯一编号和版本检查防止重复记账与并发覆盖。不写真实订单，不自动判断成交。详细参数、局限和运行方式见 `docs/strategy.md` 与 README。

## 1. 目标与边界

构建一个本地、单用户使用的 Binance Alpha 交易辅助应用，减少重复填写和点击操作。用户负责登录、平台验证以及初期看护。浏览器执行能力是第一阶段重点，策略效果和无人值守可靠性在后续阶段验证。

第一阶段输入为用户明确指定的交易链接、买卖方向、价格和数量；输出为经过核对的填表结果或订单提交结果。无需先接行情 API，即可验证执行链路。

后续逐步增加行情采集、价格计算、成交监听、超时撤单重挂、活动有效期与成本统计。账户和成交信息的获取渠道需要单独核实，不能将公共行情 API 当作个人订单状态来源。

## 2. 技术选型

| 模块 | 选型 | 说明 |
| --- | --- | --- |
| 后端框架 | FastAPI | 接收指令、查询任务、提供状态推送 |
| Python 管理 | uv | 管理 Python 环境、依赖和锁文件 |
| 前端 | Vue 3 + TypeScript + Vite | 构建操作控制台与后续数据交互页面 |
| 前端包管理 | npm | 使用 `package-lock.json` 固定依赖 |
| 浏览器自动化 | Playwright Python | 定位元素、填写表单、点击、读取页面结果 |
| 浏览器 | 本机 Chrome | 有界面运行，用户可以登录和接手 |
| 数据持久化 | SQLite3 + SQLAlchemy | 保存配置、指令、任务、订单与成交记录 |
| 数据库迁移 | Alembic | 对表结构变更进行版本管理 |

不预先指定未经验证的依赖版本。初始化时选择相互兼容的稳定版本，记录 Python、Node.js 版本，并提交两端锁文件。初期不引入 Redis、Celery 或额外数据库服务。

## 3. 架构与进程

```text
Vue 本地控制台
    │ HTTP 指令与查询 / WebSocket 状态通知
    ▼
FastAPI 后端 ───────── SQLite
    │ 单一指令通道 / 执行结果
    ▼
独立浏览器执行器进程
    │ Playwright
    ▼
Chrome 独立用户目录 → Binance Alpha 页面
```

前后端分别从源码启动，所有服务初期仅监听本机回环地址。前端通过 Vite 代理访问后端 API 和 WebSocket。

后端管理一个浏览器执行器子进程，通过本机进程间通信传递指令和事件。执行器统一拥有浏览器连接，并串行处理页面操作；不允许多个请求并发修改同一下单表单。

SQLite 由后端负责业务写入，执行器通过事件回报状态。后端使用单个服务 worker，避免多个服务进程各自启动浏览器执行器。网页刷新、WebSocket 断开不启动新任务，也不重复发送交易指令；重连后通过任务编号查询当前状态。

浏览器执行器首次启动时使用独立持久化用户目录，不占用日常 Chrome 默认配置。用户在该窗口手动登录。登录数据可保留，但会话是否继续有效由平台决定。

## 4. 控制台与第一阶段交互

第一阶段页面包含：

- 浏览器启动、连接及需要人工处理的状态。
- Alpha 交易链接与核对后的交易对信息。
- 买卖方向、价格、数量输入框。
- “仅填表”“提交订单”两个明确区分的操作。
- 指令编号、执行进度、页面反馈与错误记录。

先验证“仅填表”，随后在用户看护下使用用户指定的小额验证真实提交。程序不自行决定第一阶段的交易金额或价格。

页面暂停表示停止接收或执行后续操作，不代表撤销已经提交的订单。撤单、停止新买入、退出持仓在后续阶段分别设计，不合并为含义不清晰的单个停止动作。

## 5. 指令协议与执行流程

初期下单指令包含：

| 字段 | 用途 |
| --- | --- |
| `command_id` | 唯一指令标识，用于防止重复执行 |
| `trade_url` | 用户指定的交易页面地址 |
| `expected_symbol` | 经页面识别并由用户核对的预期交易对 |
| `side` | `buy` 或 `sell` |
| `price` | 十进制字符串 |
| `quantity` | 十进制字符串 |
| `mode` | `fill_only` 或 `submit` |

执行顺序：校验指令 → 核对交易页面与交易对 → 切换买卖方向 → 填入参数 → 回读并核对实际值 → 按模式停止或提交 → 读取结果 → 保存状态。

优先使用页面元素的语义、标签和稳定属性定位，避免固定屏幕坐标。输入框失效、控件歧义、页面币种不符或输入值不符时不提交。

指令执行状态与交易所订单状态分开保存。例如，指令可以是等待、执行中、仅填表完成、提交已确认、明确失败、需人工处理或结果未知；交易所订单另行记录未成交、部分成交、全部成交、已撤销等实际状态。

唯一指令编号与数据库唯一约束防止同一请求被重复处理，但不能单独保证外部交易恰好执行一次。点击提交后如果进程退出或页面反馈丢失，应将结果视为未知，核对订单后才允许继续。无法核对时交由用户处理，不能盲目重试。

## 6. 数据存储

数据库路径固定解析为项目根目录下 `data/alphalooper.db`，不随启动终端的工作目录变化。

计划保存以下数据：

- 应用配置和交易对配置。
- 运行任务与生命周期记录。
- 操作指令及状态转换事件。
- 已识别的交易所订单及提交反馈。
- 后续接入的成交明细、费用和统计数据。

价格和数量在 Python 中使用 `Decimal`，通过 API 及 SQLite 以规范化十进制字符串存储。不得先转为二进制浮点数；精确汇总由 Decimal 完成，不对字符串列直接进行依赖浮点转换的 SQL 求和。

时间统一保存为 UTC，界面可显示北京时间。配置中的任务时间窗口与后续积分统计日界线应明确区分。

SQLite 启用外键约束，采用短事务；使用 WAL 与合理的忙等待设置改善读写配合，但不假设支持多个并行写入者。高频盘口原始数据暂不纳入本阶段存储范围。

数据库迁移脚本提交 Git。数据库、WAL/SHM 文件、浏览器用户目录、日志均不提交。浏览器会话存储在独立用户目录中，不复制到业务数据库。

## 7. 异常处理与恢复

- 登录失效或出现验证：暂停新操作，显示需要人工处理。
- 页面元素缺失或结构变化：记录错误，停止本次操作。
- 下单结果未知：禁止自动重发，先核对订单。
- 执行器异常退出：后端标记异常；恢复前核对未结束指令和现有订单。
- 后端重启：不自动恢复提交动作，先展示待核对任务。
- 手动干预页面：每次提交前重新核对交易对、方向、价格与数量。

日志不记录密码、Cookie、令牌等会话内容。需要错误截图时仅本地保存，并注意截图可能包含账户信息。

## 8. 第一阶段验收

1. 本地控制台与后端能从源码启动。
2. 能打开有界面的 Chrome，用户能登录及完成验证。
3. 能通过指定链接切换交易对，并核对当前页面。
4. 买入和卖出表单均能自动填写、回读并核对。
5. “仅填表”不触发真实提交。
6. 用户看护下，能提交指定买单与卖单并返回明确结果；不要求提交后立即成交。
7. 同一指令重复请求不会重复操作；未知结果不会自动重发。
8. 刷新控制台不重复下单，能恢复显示任务状态。
9. 登录失效、页面不符、输入不符时能暂停并显示原因。

验证包括实际页面可行性检查，以及针对重复指令、未知结果、Decimal 精度和状态恢复的必要测试。真实下单验证与模拟测试分开记录。

## 9. 后续演进

第一阶段通过后，再接入行情与外部计算程序。外部程序使用同一指令边界，不直接操作浏览器。随后补充订单成交监听、撤单确认、部分成交处理、超时重挂和成本预算。

最终再评估夜间长时间运行。浏览器链路可用不等于策略成本可控，也不等于已经具备无人值守条件；这些分别通过数据与运行记录验收。

## 11. 模拟账本实现

迁移 0002 增加 research_tasks/research_orders/research_events/research_fills；与真实交易隔离。金额以十进制字符串保存在文本/JSON 字段中，通过 Decimal 计算。事件写入、委托状态、成交和任务快照在同一 SQLite BEGIN IMMEDIATE 事务内提交。相同事件编号/内容重试返回当前状态；不同内容复用编号或版本过期返回 409。

任务参数固定，快照核对币种、链、合约与计价币，记录事件前校验盘口时效。成交采用明确事件；成交及手续费以计价币计入移动平均成本账本。每日划分待确认，本阶段按任务累计。真实手续费币种、订单关联、提交结果未知恢复及订单监听仍需在后续接入真实数据时实现。
